# Upstream limitations, workarounds, and what may justify a fork

The editor's behaviour is built on third-party libraries that are not ours: ProseMirror and
`prosemirror-tables`, Yjs and `y-prosemirror`, Monaco, and the browser's own editing surface.
Where one of them cannot express what a docx needs, the work routes around it, and the routing
is worth recording — otherwise the workaround outlives the defect, nobody remembers why a piece
of code is shaped oddly, and a fix upstream is never noticed.

This is the same practice docx4j keeps for Apache FOP (see `../docx4j/CLAUDE.md`, "FOP defects
and limitations", whose items carry the measurement, the named docx4j-side workaround and the
upstream status, with the fix itself on a branch of a fork and a JIRA drafted for Jason to
file). ED-001 §4.1 is the case that prompted this file.

## How to record an item

One numbered item per limitation, in the table below, with a section beneath it when there is
more to say than a row holds. Each item states:

1. **The library and version** the limitation was observed in.
2. **What it cannot do**, concretely, and how it shows up in the editor (a failing case, not a
   general complaint).
3. **The workaround in our code**, named so it can be found and deleted later: the file, the
   function, and a `// UPSTREAM-n:` comment at the site pointing back to this item.
4. **What a fork would cost**, if a fork is the alternative: the surface that would have to be
   maintained, and whether the change is plausibly acceptable upstream.
5. **Upstream status**: issue or PR link, or "not raised". Where a fix is plausible upstream,
   raising it is preferred to carrying a fork; where we do fork, the fork lives on a branch
   named for the item and the upstream submission is drafted for Jason to file, as docx4j does
   with FOP.

Close an item when the fixed version is released *and* we build against it; delete the
workaround in the same change, and leave the item here marked closed with the version that
fixed it.
